# JSON API — 読みは公開、書きは Cookie

- 状態: 実装済み（#36）
- 前提: `docs/004-layers.md`（層の分け方）、`docs/001-mvp.md` 5 章（URL 設計）

## 1. なぜ

いまは全部サーバー側で描いている。そのうち処理をクライアント側へ持ってきて、
API 経由で情報を取る形にしたい。#28 で操作を `actions/` `views/` に寄せてあるので、
**入り口を足すだけ**で済んだ。SQL も認可も検証も、1 行も書き足していない。

```ts
export const PATCH: RequestHandler = (event) =>
  json(event, (ctx, input) => updateTimeline(ctx, event.params, input));
```

これが `+server.ts` の中身の全部。画面側の `+page.server.ts` が
`submit()` を使うのと、**同じ操作を、違う入り口から呼んでいるだけ**。

## 2. 認証

**Cookie。同一オリジン専用。** Web UI は同じオリジンなので、いまのセッションが
そのまま使える。MCP 用のトークン認証は別（#34）。

読みは公開で認証不要。年表は全部公開で読めるので、隠す理由がない。

### CSRF

Cookie で誰かを決めている以上、他所のページから叩けると CSRF になる。2 つで塞ぐ。

- **`Origin` が自分のオリジンと一致すること。** 実際に止めているのはこれ
- **本体があるときは `Content-Type: application/json` に限る。**
  `text/plain` は preflight を起こさない simple request なので、許すと
  `Origin` だけが頼りになる。念のための二重化

本体の無い書き込み（`DELETE`）には `Content-Type` を求めない。`fetch()` は
そういう要求に付けないし、送るものが無ければ紛れ込ませるものも無い。

**CORS は開けない。** 開けた瞬間にこの前提が崩れる。

## 3. URL

`/-/` はアプリ機能側の目印（`docs/001-mvp.md` 5 章）。slug は先頭が英数字なので
衝突しない。同じ規則を API でも使う。これが無いと `timelines` という slug の
年表が `POST /api/@u/-/timelines` に食われる。

### 読み（公開）

```
GET /api/timelines                     全部の年表（更新の新しい順）
GET /api/@:username                    その人の年表一覧
GET /api/@:username/:slug              年表本体
GET /api/@:username/:slug/-/notes/:id  ノートの歴代
```

### 書き（Cookie）

```
POST   /api/@:username/-/timelines                  年表を作る
PATCH  /api/@:username/:slug                        年表を直す
DELETE /api/@:username/:slug                        年表を消す

POST   /api/@:username/:slug/-/entries              行を足す（into で束ねに足す）
PATCH  /api/@:username/:slug/-/entries/:id          行を直す
DELETE /api/@:username/:slug/-/entries/:id          行を消す

POST   /api/@:username/:slug/-/entries/:id/detach   束ねから外す
POST   /api/@:username/:slug/-/entries/:id/reorder  束ねの並びを動かす
POST   /api/@:username/:slug/-/entries/:id/merge    2 行を束ねる
POST   /api/@:username/:slug/-/entries/:id/place    自分の年表に載せる
```

`GET` は本体を読まず、クエリ文字列を入力にする。

## 4. エラー

```json
{ "error": { "code": "slug_taken", "message": "slug「x」は既に使われています" } }
```

status は `AppError.kind` から決まる（`docs/004-layers.md` 4 章）。

| kind | status | 画面 | API |
|---|---|---|---|
| `invalid` | 400 | 欄に戻す | JSON |
| `unauthenticated` | 401 | `/login?redirect=` へ | JSON |
| `forbidden` | 403 | エラーページ | JSON |
| `notFound` | 404 | エラーページ | JSON |
| `conflict` | 409 | 欄に戻す | JSON |

**ほんとうに扱いが分かれるのは `unauthenticated` だけ。** 画面には行き先が
あるのでログインへ送るが、API には送る先が無いので 401 を返す。判断は同じ。

**`code` で分岐すること。** `message` は人が読むためのもので、文言を直した
瞬間に壊れる。`unauthenticated` にも既定の code（`sign_in_required`）を
持たせてあるのは、これが API でいちばん出るエラーだから。

## 5. 決めなかったこと

- **作成に 201 を返していない。** 全部 200。呼ぶ側は自分の UI なので、
  返ってくる ref（`{ username, slug }` など）があれば足りる。公開 API に
  するときに考え直す
- **ページングが無い。** `GET /api/timelines` は 100 件まで（`listAllTimelines`
  の既定）。年表そのものは全件返す。720 件で 130KB ほどなので、いまは困らない
- **バージョンを URL に入れていない。** 使うのが自分の UI だけのうちは、
  壊れたら両方直せばよい。外に出すときに考える
