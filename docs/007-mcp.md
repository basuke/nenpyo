# MCP サーバー — AI クライアントから年表に書く

- 状態: 実装済み（#34）
- 前提: `docs/004-layers.md`（層）、`docs/006-api.md`（API）、`docs/003` 5 章（帰属）

## 1. なぜ HTTP 一択なのか

AI クライアントと繋いで、登録は AI にしてもらう。これがいまどきの UI で、
そのためには**ホストされた AI クライアントから繋がる**必要がある。

MCP の仕様には transport による分岐がある。

- **stdio（手元で動く）** … `SHOULD NOT follow this specification, and instead
  retrieve credentials from the environment`。**OAuth をやるなと書いてある**
- **HTTP（遠隔）** … OAuth 2.1 に従う

手元で動かすなら設定ファイルにトークンを置けばよいが、それでは
「AI クライアントから繋ぐ」にならない。**HTTP 一択なので、OAuth 2.1 は必須。**

## 2. セッションが仕様から消えた

現行リビジョン（2026-07-28）の Streamable HTTP は、それ以前と形が違う。

> * Removal of the GET stream endpoint.
> * Removal of protocol-level sessions.

- サーバーが用意するのは **POST を受ける 1 本だけ**
- `Mcp-Session-Id` は**無視する。発行も反響もしない**
- GET / DELETE には **405**
- 応答は `application/json` の単一オブジェクトでよい（SSE は任意）

**つまり Durable Objects が要らない。** 半年前なら「セッションを DO に持つ」が
定石だったが、いまは**素の Worker のステートレスな POST ハンドラ**が正解の形。

古い版のクライアントとも話せるようにしてある。`initialize` から始める流儀で、
いま出回っているものの多くはこちら。**サーバー側の実装は同じ**で、違うのは
初手の握手があるかどうかだけ。

## 3. MCP サーバーは「認可サーバー」ではない

ここがいちばん分かりにくい。役割が 2 つに分かれる。

| | 誰が | 仕事 |
|---|---|---|
| Resource Server | `/mcp` | Bearer を検証して tool を動かす |
| Authorization Server | nenpyo.net 自身 | **ユーザーを認証して**トークンを発行 |

そして **いまの GitHub ログインが「AS の中のユーザー認証」にそのまま収まる。**

```
AI クライアント → nenpyo.net の /authorize → GitHub でログイン → 戻る
                       ↓ nenpyo.net が自分のトークンを発行
AI クライアント → nenpyo.net の /mcp（Bearer）
```

AI クライアントは GitHub を見ない。見るのは nenpyo.net だけ。
**`allowed_github_ids` の allowlist もそのまま効く**ので、クローズド運用を
保ったまま MCP を開けられる。

AS を外に出さなかったのはこれが理由で、出すと allowlist を移すか二重に持つことになる。

## 4. 組み立て

`@cloudflare/workers-oauth-provider` が AS の面倒な部分（PKCE、`resource`、
トークン発行、Client ID Metadata Documents）を引き受ける。

```
worker/index.ts            OAuthProvider が default export を持つ
  apiRoute: "/mcp"      →  src/lib/server/mcp/http.ts  枠（405・Origin・ヘッダ検証）
                              └ mcp/server.ts          JSON-RPC
                                  └ mcp/tools.ts       tool
                                      └ actions/views  操作（画面や API と同じもの）
  defaultHandler        →  SvelteKit（画面と /api、そして /authorize）
```

**MCP は 3 つ目の入り口でしかない。** 画面が `page()` / `submit()`、API が
`json()`、MCP が tool。下は同じ `actions/` を通り、同じ `AppError` が返る
（docs/004-layers.md）。

### 同意画面は普通のページ

`OAuthProvider` は `authorizeEndpoint` を自分では処理せず `defaultHandler` へ
渡す。だから `/authorize` は SvelteKit のルートとして書けて、**ログインは
既存の仕組みがそのまま効く**。未ログインならログインへ送られ、戻ってくれば
クエリごと同意画面が続く。

JavaScript を要らない形で書いてある。何を許すかを決める画面なので、
スクリプトが動かなくても壊れないほうがよい。

### adapter-cloudflare と喧嘩する

**アダプタは `main` の指す先に自分の生成物を書く。** `main` を自前エントリに
すると、`pnpm build` のたびに上書きされて消える。

逃げ道はアダプタの `config` オプションで、書き出し先だけを別の設定に分ける。

```
wrangler.svelte.jsonc   アダプタだけが読む。main = .svelte-kit/cloudflare/_worker.js
wrangler.jsonc          デプロイ用。main = worker/index.ts
```

包みが `worker/` にあって `src/` に無いのも同じ事情。**ビルド成果物を
import する**ので、`src/` に置くと `tsconfig` の `checkJs` が生成物まで
追いかけて、svelte-check が 1000 件のエラーを出す。

### PUBLIC_ORIGIN

トークンをどの資源に結びつけるか（audience）は仕様が MUST で検証を求めている
ので、`resource` は固定したい。だが決め打ちにすると開発で繋がらないので、
`wrangler.jsonc` の `vars` から読む。

`issuer` のほうは provider がリクエストの origin から導く。**`wrangler dev` は
`routes` の `custom_domain` を模す**ので、開発中も Worker からは nenpyo.net に
見えており、上書きは要らない。

**MCP をローカルで試すときは https で立てること。** OAuth の認可サーバーは
HTTPS でなければならず、provider が起動時に弾く。

```
npx wrangler dev --local-protocol https
```

## 5. スコープと tool

**「誰として書くか」ではなく「何をしてよいか」で切る。** ノートは誰が書いても
持ち主のものなので（docs/003 5 章、#35）、誰として振る舞うかを分ける必要がない。

| scope | tool |
|---|---|
| `timeline:read` | `search_events` `list_timelines` `get_timeline` |
| `note:write` | `write_note` |
| `event:write` | `add_event` `place_entry` |

同意画面では**求められたものを 1 つずつ外せる**。読みだけ許して書きは断る、が
できる。既定は全部チェックが入っているが、決めるのは持ち主でクライアントではない。

`place_entry` が `event:write` にあるのは、事実を作りはしないが年表に載る行が
増えるから。

**使えない tool は `tools/list` に出さない。** 出すと AI が呼んでから断られる。
それでも名前を知っていれば呼べるので、呼ばれたら 403 で止め、
**何があれば足りるかを添える**（RFC 6750 3.1）。これが無いとクライアントは
足りない分を足した再認可に進めない。

```
403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", scope="event:write"
```

## 6. スコープはトークンの props に自分で入れる

**provider は許した範囲をハンドラに渡してくれない。**

> The provider does not expose a standard effective-token authorization context
> to API handlers or enforce operation-level scope policy.

`completeAuthorization()` の `scope` は OAuth の記録で、`/mcp` からは見えない。
だから `props` にも入れる。渡し忘れると「全部できる」でも「何もできない」でもなく、
**黙って何も見えなくなる**（tool が 1 つも出ない）ので、`TokenProps` の型で必須にした。

## 7. tool の失敗は tool の結果として返す

操作が投げた `AppError` は、JSON-RPC の失敗ではなく `isError: true` の結果にする。

「他人の年表は編集できません」は protocol の故障ではなく、**AI が読んで
やり直せる筋の話**なので、中身を渡すほうが噛み合う。JSON-RPC のエラーにするのは
protocol の話（知らない method、知らない tool、ヘッダの不一致）だけ。

スコープ不足だけは例外で、HTTP の 403 として返す。`WWW-Authenticate` が要るのと、
再認可という道があるため。

## 8. 事実の正しさは別問題

#35 で決まったのは**帰属**の話で、AI が用意した文も載せた人の持ち物になる。
だが `add_event` は**事実を書く**ので、そこは帰属では解けない。

いまは `add_event` の説明文で出典を促しているだけで、`links` を必須にはして
いない。必須にすると「出典の無い出来事は足せない」ことになり、人が画面から
足すときとの整合が取れなくなる。**出典の無い行を画面で区別するか**は未決
（#10 や表示の議論と一緒に決めるのがよい）。

## 9. 決めなかったこと

- **SSE を使っていない。** 応答は単一の JSON。長い処理も進捗通知も無いので要らない
- **`subscriptions/listen` を実装していない。** 年表が変わったことを AI に
  知らせる道はまだ無い
- **resources / prompts を出していない。** tool だけ
- **DCR を残してある。** 仕様は非推奨にしたが、いま出回っているクライアントの
  多くがまだこちらで登録してくる。塞ぐと繋がらない。Client ID Metadata
  Documents も有効にしてあるので、対応したクライアントはそちらを使う

## 10. 出す前にやること

**KV namespace を作る。** MCP の OAuth はクライアントの登録・認可コード・
トークンをここに置く（年表のデータは D1 のまま）。

```
npx wrangler kv namespace create OAUTH_KV
```

出てきた id を `wrangler.jsonc` の `kv_namespaces` に入れる。
**入れないとデプロイが落ちる。**

同意画面の見た目と、実際の AI クライアントからの接続は本番でしか確かめられない。
ローカルでは自己署名の証明書になるので、クライアントによっては繋がらない。
