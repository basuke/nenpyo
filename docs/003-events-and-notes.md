# イベントとノートの分離

作成日: 2026-08-20
ステータス: 実装済み（Epic #3）。実地で分かったことを 11・14 章に追記

MVP では 1 つの `Event` が「いつ・何が起きたか」と「それをどう読むか」を
まとめて持っている。この文書は、その 2 つを分ける設計をまとめたもの。
議論の経緯は Issue に、結論はここに残す。

---

## 1. 何が問題か

松尾公也さんの年表を読むと、タイトルの末尾に括弧でキャッチコピーが付いている。

```
AKB48 劇場オープン(会いに行けるアイドル)
シムシティ発売(勝利条件のない箱庭)
Macintosh Portable(膝を潰す重さの初代)
TSMC設立(設計と製造を切り離すという発明)
```

720 件のうち **595 件が末尾に括弧付き**で、その大半が事実ではなく**松尾さんの評**である。
`description` も同じで、「専門特化 AI より汎用 LLM が幅を利かせる現在を先取りしている」は
1939 年に起きた事実ではなく、2026 年から振り返って書かれたものである。

これらは**属人的**である。1937 年にレンズマンの連載が始まったことは誰にとっても同じだが、
それを「固有名詞の予言が当たった稀有な例」と読むかどうかは人による。

イベントが将来いろいろな年表で共有されることを前提にすると、
**1 つの出来事に複数のノートが付く**のが自然な形になる。

## 2. 決めたこと

| | 持つもの | 性質 |
|---|---|---|
| `events` | いつ・何が起きたか、出典 | **客観**。名寄せの対象になる素材 |
| `notes` | キャッチコピー、説明、その根拠 | **属人**。1 つの出来事に何本でも |
| `timeline_entries` | 年表の 1 行。どの note を採用したか | 年表ごとの**編集判断** |
| `timeline_entry_events` | その行が指すイベント（1..N） | 束ねも同じ仕組みで表す |

`links` が `events` と `notes` の両方にある。
「レンズマンの Wikipedia」はイベントの出典だが、
「マスクが SpaceX 創業の動機として公言しているソース」は松尾さんのノートの根拠であって、別物。

## 3. なぜ Note は Event ではなく Entry に紐づくのか

束ねられたイベントの description を見ると、はっきりする。

> **初代iMac発売/ドリームキャスト発売/Google創業**
> 半透明ボンダイブルーの iMac が Apple 復活の狼煙。ドリームキャストはモデム標準搭載で
> ネット対戦を家庭へ。Google はガレージで創業。**1998 年は再起動の年。**

最後の一文は iMac についてのものでも Google についてのものでもない。**3 つ並んでいることに対するノート**である。

そして「1998 年は再起動の年」は iMac 発売という事実の属性ではなく、
**松尾さんがその年表で 3 つを束ねた編集判断**である。別の人は iMac だけ拾うかもしれない。

だから束ねは年表側になければならない。`timeline_entries` を導入し、
そこが note を指す。

**entry はつねに自分のもの**（`timeline_id` を持つ）で、コピーされることはない。
他人の年表から引いてくるとき、共有されるのは **event と note への参照**だけで、
entry は必ず新規に作られる。

## 4. 束ねに種別（kind）を持たせない

`timeline_entry_events` は 1..N。**単独のイベントは要素数 1 の束ね**として扱う。

`kind = 'simple'` のときだけ `event_id` を直接持つ、という最適化はしない。
参照経路が二分岐して、読む側のコードが 2 通りになるほうが高くつく。
720 行規模の SQLite で JOIN 一段のコストは無視できる。

束ねかどうかは要素数で分かるので、種別を持つ必要そのものがない。

## 5. Copy on Write

**参照はまず参照として置かれ、値を変更しようとしたときに複製される。**

他人の年表からイベントを引いてくると、最初は同じ `events` 行を指す。
そのタイトルを直したくなった時点で行を複製し、自分の entry を新しいほうへ付け替える。
note も同じ。

裏返すと、**自分が所有するものを直したときは複製されず、参照している全員に伝わる。**
松尾さんが `シムシティ発売` を直せば、引用しているすべての年表が変わる。

MVP ではこれを**受け入れる**。events は素材ライブラリであり、事実の訂正は伝わるべきである。
「誤字の修正」と「意味を変える改稿」を区別する仕組みは持たない（→ 9 章）。

## 6. 削除しない

CoW を入れると `A → B → C` という派生の連鎖ができる。ここで B を消すと C の来歴が切れる。

git を参照すると答えが出る。**git はオブジェクトを削除しない。**
消えるのは「どこからも到達できなくなったもの」だけで、
だから親リンクが壊れるという状況が原理的に起きない。

これをそのまま採る。

- **参照されているものは削除できない**（`ON DELETE RESTRICT` 相当。D1 なのでアプリ側で担保する）
- 派生エッジも参照に数える。C が生きている限り B は消せない
- **論理削除フラグは持たない。** 到達可能性だけで足りる

ユーザーの実感とも矛盾しない。「自分の年表から消す」は entry の参照を外すことで、
それはいつでもできる。DB に残るのは他人がそれを土台にしている場合だけで、
そのとき消せないのは正しい。

## 7. 派生関係を first class にする

来歴は `source_note_id` のような**列ではなく、行として持つ**。

```sql
derivations (id, kind, ancestor_id, descendant_id, created_at, created_by, reason)
```

削除対策としては 6 章で片が付いている。実体にする理由はそれとは独立にある。

- **来歴にメタデータが乗る。** 「いつ・誰が・なぜ複製したか」は列には書けない。
  「松尾さんのノートを引用して書き換えた」という行為自体が記録に値する
- **親が複数持てる。** 2 つのノートを統合して 1 つにすることはありうる。
  git のマージコミットに当たる。列では表現できない
- **推移閉包を張れる。** 必要になれば `A → C` を直接持てる。列では親 1 段しか持てない

### 副産物

CoW で「1998 年 iMac 発売」が複数行に増えても、
**コピー由来のものは `derivations` を辿れば同一物だと機械的に判る。**
名寄せが本当に必要なのは「別々に手入力された同じ出来事」だけになり、
`001-mvp.md` 8.4 で難問としていた共有客観 DB の名寄せは、その分だけ削れる。

## 8. 派生と改版は別の軸

git には性質の違う関係が 2 つある。混ぜない。

1. **派生**（fork / copy）— 誰のノートから来たか。**人と人のあいだの来歴**
2. **改版**（version）— 同じノートが時間とともに変わる履歴

`derivations` も CoW も 1 の話である。
そして 5 章の「自分の編集が参照元へ伝搬する」問題は、**2 を持っていないから起きている**。
note が immutable で entry が特定の版を指すなら、書き直しても引用側は動かない。

ただし append-only にすると「最新版を指すポインタ」（git の ref に当たるもの）が要るし、
誤字修正のたびに行が増える。MVP には重い。

**今回は 1 だけ実装する。** 2 は直交する別の軸なので、後から別テーブルで足せる。

## 9. スキーマ

```sql
-- 客観の核。単体では表示しない（かならず entry を通して見る）
events                 id, year, precision, title, links, created_by, …

-- 属人のノート。1 つの出来事に何本でも
notes                  id, author_id, tagline, body, links, …

-- 年表の 1 行。採用したノートを固定して指す
timeline_entries       id, timeline_id, note_id, position

-- その行が指すイベント（1..N）。単独は要素数 1
timeline_entry_events  entry_id, event_id, position

-- 派生の来歴。events と notes の両方を扱う
derivations            id, kind, ancestor_id, descendant_id, created_at, created_by, reason
```

`timeline_entries.note_id` に**固定で刺さる**ことが重要である。
後から人気順や推薦のロジックを入れても、**既存の年表の文言が勝手に変わらない**。
年表は編集物なので、この性質は守る。

「引用時にどの note を勧めるか」は UI の問題であって、スキーマは何も持たなくてよい。

## 10. 「テーマの糸」との関係

`001-mvp.md` 8.3 の「テーマの糸」（`src/threads.js` の 20 本）は、
複数のイベントを束ねて 1 つのノート（`lead`）を与えるという点で束ねに似ている。が、**別物**である。

- **糸は年表を横断する。** 複数の timeline_entry を跨いで拾い直す
- **束ねは 1 エントリの中に閉じている。** 1 行として表示される

同じ構造には乗らない。糸は別レイヤーのまま残す。

## 11. 既存 720 件の移行

括弧は 2 つの役割を兼ねている。**位置がほぼそのまま判定基準になる。**

仕分けの結果は `curation/` の 3 つの表にあり、変換スクリプトはそれを読むだけで
判断を持たない。数字はスラッシュの分割を織り込んだあとのもの。

| | 件数 | 扱い |
|---|---|---|
| 末尾に括弧 | 586 | 452 件からキャッチコピーを切り出し、134 件は事実補足のみ |
| 途中に括弧 | 15 | **全件が略称・言い換え。タイトルの一部として残す** |
| 括弧なし | 154 | tagline なしの note（body だけ） |

結果は **entry 726 件 / event 755 件 / キャッチコピー 436 件**。

「位置がそのまま判定基準になる」という見立ては、途中括弧 15 件がすべて事実
補足だったことで裏が取れた。唯一の例外だった `Xerox Alto(GUIの原点)` は
スラッシュの分割で先に片付いている。

末尾括弧のうち、事実補足に落ちるのは 3 パターン。前 2 つは正規表現で確実に取れる。

- 人名 — `鉄人28号 連載開始(横山光輝)`
- 年範囲 — `ファウンデーション 連載開始(〜53年三部作)`
- 純粋な補足 — `2001年宇宙の旅 公開(日本公開も同年)`

3 つ目がグレーで、`(ジョブズの雌伏とWebの生まれた機械)` のような明白な tagline との境目に
数十件たまる。機械で仕分けてグレーだけ人力で見る。

### スラッシュを含む 47 件は先に分割する

`/` は区切り記号として**信用できない**。3 つに分かれる。

- **割ってはいけない**（名前の一部）— `IBM System/360` `DOS/V登場` `I/O創刊`、
  原題と邦題（`GHOST IN THE SHELL/攻殻機動隊` `her/世界でひとつの彼女`）
- **割るべき**（無関係な出来事の並置）— `コロコロコミック創刊/Apple II 発売`
- **割ると壊れる**（束ねること自体が見方）— `Wii/PS3発売(体を動かす操作の一般化)`

3 つ目が本文書の compound になる。47 件しかないので機械判定は諦めて手で仕分ける。
**tagline の分解より先にこれをやる**（分割してからノートを付けないと、付け直しになる）。

実際に 47 件を読んだ結果は **keep 11 / compound 27 / split 6 / tagline 3**。
「割るべき」と見積もっていた 15 件は 6 件しかなく、**大半は割るとノートが宙に浮いた**。
同じ年の複数の出来事を束ねて一つの見方を与えるのが松尾さんの編集手法そのもので、
compound はその器として正しかった。

想定していなかった 4 つ目が出た。**`/` の片側が出来事ではなく、もう片方へのキャッチコピー**に
なっているもの（`LTE(Xi)サービス開始/スマホの本格普及`）。これを見つけたことで、
「出来事ではなく傾向」をどう持つかという問題が畳めた（14 章）。

## 13. 実装して分かったこと

設計そのものは変えずに済んだ。実地で決めたことと、危うかったところを残す。

### 「出来事ではなく傾向」に種別は要らなかった

`スマホの本格普及` `Vibe Coding元年` のように、離散的な出来事でないものが
当初 9 件あり、`events` に種別（`occurrence` / `trend`）を持たせる案を検討した。

キャッチコピー寄りのものを tagline へ振り分けたら 6 件に減り、残りは
`ファジー家電ブーム` `「J-POP」という呼び名が広まる` のように**実際に起きたこと**に
なった。拡散的ではあるが `precision: 'year'` の event として素直に置ける。
**スキーマに種別は足していない。**

### 参照の付け替えでノートが黙って消える

束ねの子タイトルを作ると、元タイトル末尾の括弧がそこから落ちる。
`ポン発売/オデッセイ発売(ビデオゲーム産業の開幕)` のノートが 12 件ぶん消えていた。

**構造を組み替える作業では、移し先の無いデータが黙って落ちる。**
`pnpm data:check` に「末尾の括弧の行き先がないと落ちる」検査を足してある。

### 束ねかどうかは読む側には要らない区別

表示で束ねを罫線と行頭の点で括ってみたが、やめた。元データと同じ `/` 区切りで
読める。構造の都合を見た目に持ち込むと、`IBM System/360発表` のように名前へ
`/` を含むタイトルと張り合うことになって、かえって読みにくい。

**束ねが効くのは編集のときだけ。** 編集画面には、先頭のイベントしか直せないことを
明示してある。

### 削除しない設計は D1 の外部キーがそのまま効く

参照されている `event` を消そうとすると `FOREIGN KEY constraint failed` で落ちる。
アプリ側の到達可能性チェックは、その手前で親切に振る舞うためのもので、
最後の砦は DB が持っている。
