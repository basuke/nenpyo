# 関心年表 MVP 要件定義

作成日: 2026-08-18
最終更新: 2026-08-18（第 3 版）
ステータス: 合意済み（実装着手可）

---

## 1. 目的

構想段階で積み上げてきたデータモデルの議論を、**実際に動くもの**の上で検証する。
最初の実データとして松尾公也さんの「SF・コンピューター技術ライフライン」を投入し、
「実データを入れると構造がどう変わるか」を見ながらモデルを詰めていく。

このフェーズのゴールは完成品ではなく、**触れる叩き台**をつくること。

締め切りは設けない。ただし松尾さんとの共同制作なので、早く見せられるほどよい。

---

## 2. 前提と制約

- **閲覧は誰でも可能**。ログインしていない訪問者もタイムラインを読める。
- **編集はオーナーのみ**。他人のタイムラインは閲覧専用。
- サインアップはクローズド運用。allowlist に載った GitHub アカウントのみ。
- 後から構造を変える前提で作る。マイグレーションしやすさを優先し、作り込みすぎない。
- UI の作り込みは最小限。データ構造の検証が主目的。
- 当面は検索エンジンに載せない（`noindex`）。品質上の判断であり、権利上の制約ではない。

## 3. 技術スタック

| 領域 | 選定 |
|---|---|
| フレームワーク | SvelteKit（`adapter-cloudflare`） |
| 実行環境 | Cloudflare Workers |
| データベース | Cloudflare D1（SQLite） |
| DB アクセス | **生 SQL**。マイグレーションは `wrangler d1 migrations` |
| 認証 | GitHub OAuth |
| セッション | **D1 のセッションテーブル**＋ Cookie に session id |

現行リポジトリは Hono + Vite で組まれており、`src/index.ts` に「近日公開」ページが
直書きされている。これは破棄し、SvelteKit で組み直す。
Vitest / GitHub Actions / カスタムドメインの設定は流用する。

ORM は入れない。「後から構造を変える前提」であるぶん、SQLite の挙動が
そのまま見えているほうが判断しやすい。行の型は手書きで用意する。

## 4. 認証と権限

### 4.1 GitHub OAuth を採用する理由

URL にユーザー名を含める設計（後述）を採るため、ユーザー名の一意性が重要になる。
GitHub のアカウント名空間をそのまま借りることで、一意性の管理を自前で持たずに済む。
また想定する初期ユーザー層は全員 GitHub アカウントを持っている。

OAuth App そのものの作り方・台帳・secret の回し方は [`002-github-oauth.md`](002-github-oauth.md)。

### 4.2 要求スコープ

**最小限に留める。** 取得するのは以下のみ。

- GitHub の数値 ID
- ユーザー名（login）
- 表示名
- アバター URL

リポジトリへのアクセス権限は**要求しない**。許可のハードルを下げるため。

### 4.3 ユーザー名の可変性への対応

GitHub のユーザー名は本人が後から変更できる。したがって:

- **内部の不変キーは GitHub の数値 ID**（`github_id`）
- **ユーザー名は表示・URL 用の可変フィールド**として別に保持
- ログイン時に最新のユーザー名を取得し、変更されていれば更新する

### 4.4 セッション

- `sessions` テーブルに実体を持ち、Cookie には session id のみを入れる
- Cookie 属性: `HttpOnly; Secure; SameSite=Lax; Path=/`
- SvelteKit の `hooks.server.ts` で毎リクエスト解決し、`locals.user` に載せる
- 失効・強制ログアウトは行の削除で済ませる

### 4.5 サインアップの制御

`allowed_github_ids` テーブルに載っている GitHub 数値 ID のみログインを通す。
外れたアカウントは OAuth 自体は成功させたうえで「準備中」画面を返す。
環境変数だと追加のたびにデプロイが要るが、テーブルなら D1 に 1 行 INSERT で済む。

初期登録: `42601`（basuke）, `235002527`（matsuo-koya）

### 4.6 権限モデル

| 操作 | 未ログイン | ログイン済（非オーナー） | オーナー |
|---|---|---|---|
| タイムライン閲覧 | ○ | ○ | ○ |
| ユーザーのタイムライン一覧閲覧 | ○ | ○ | ○ |
| タイムライン作成 | × | ○ | ○ |
| タイムライン編集・削除 | × | × | ○ |
| イベント追加・編集・削除 | × | × | ○ |

## 5. URL 設計

ユーザー名に `@` を前置し、アプリ側のパスと名前空間を分ける。
これにより**予約語リストが不要**になり、今後どんなパスを足しても既存ユーザー名と衝突しない。

```
/                                       全タイムライン一覧
/login                                  GitHub OAuth 開始
/auth/github/callback                   OAuth コールバック
/logout                                 ログアウト

/@{username}                            ユーザーのタイムライン一覧
/@{username}/-/new                      タイムライン作成
/@{username}/{slug}                     タイムライン本体（イベント一覧）
/@{username}/{slug}/-/edit              タイムライン編集
/@{username}/{slug}/-/events/new        イベント追加
/@{username}/{slug}/-/events/{id}/edit  イベント編集
```

ユーザー配下のアプリ機能は GitLab 方式で `/-/` を挟む。
slug の形式（後述）は先頭が英数字なので、`-` が slug と衝突することは原理的にない。
タイムライン配下は現時点では全てアプリ側のパスだが、将来イベントに slug を
振りたくなったときのために `/-/` を揃えておく。

**slug の形式**: `^[a-z0-9][a-z0-9-]{0,49}$`、同一オーナー内で一意。
作成フォームで**必須入力**とする。日本語タイトルからの自動生成は現実的に機能しないため。

**実装メモ**: SvelteKit のルートディレクトリ名で `@` はレイアウトリセット記法と
字面が被る。`@[username]` がそのまま通るか、16 進エスケープ `[x+40][username]` が
必要かは実装時に確認する。

## 6. スコープ

### 6.1 今回つくるもの

| # | 機能 | 内容 |
|---|------|------|
| F-1 | GitHub ログイン | OAuth による認証。最小スコープ。allowlist で制限 |
| F-2 | タイムライン一覧 | **更新順（新しいものが上）** に表示。トップ `/` は全件、`/@{username}` はそのユーザーのもの |
| F-3 | タイムライン作成・編集 | タイトル・slug・説明を持つタイムラインを作成・編集・削除 |
| F-4 | イベント一覧表示 | 1 タイムラインのイベントを**年ごとにグルーピングした縦一列**で表示。未ログインでも閲覧可 |
| F-5 | イベント追加 | 年・タイトル・説明・カテゴリを入力して追加 |
| F-6 | イベント編集・削除 | 既存イベントの修正と削除 |
| F-7 | データ投入 | 松尾さんの年表 720 件を初期データとして流し込むスクリプト |

### 6.2 今回つくらないもの（意図的な先送り）

構想として合意済みだが、この MVP では実装しない。

- イベントの多対多所属（複数タイムラインへの掲載）
- 共有客観 DB と名寄せ・マージ
- フォーク / プルリクエスト的な仕組み
- パーソナル度およびその周辺の軸（未確定のため）
- 公開範囲の三段階制御（public / friends / private）
- AI によるイベント自動分類・自動関連づけ
- 多言語対応・翻訳
- タイムラインをクエリとして動的に評価する仕組み（→ 8.3 参照）

これらは「入れない」のではなく「今は入れない」。データモデルは後で拡張できる形にしておく。

## 7. データモデル

### User

| フィールド | 型 | 備考 |
|---|---|---|
| id | ID | 内部 ID |
| github_id | integer | **不変キー**。一意 |
| username | string | GitHub の login。URL・表示に使用。**変更されうる**。一意 |
| display_name | string | 表示名 |
| avatar_url | string | |
| created_at / updated_at | datetime | |

未登録ユーザーの行を**先行して作成できる**。GitHub の数値 ID・login・アバターは
公開情報なので、本人がログインする前にレコードだけ用意しておける。
本人が初めてログインしたとき、`github_id` の一致で既存行に紐づく。

### Session

| フィールド | 型 | 備考 |
|---|---|---|
| token_hash | string | Cookie に入るトークンの **SHA-256**。平文は保存しない |
| user_id | ID (User) | |
| expires_at | datetime | |
| created_at | datetime | |

Cookie に入るのは 256 ビットの乱数そのもので、DB にはそのハッシュだけを置く。
DB の中身が漏れても、そこから成りすませるトークンは作れない。
ソルトも反復もしないのは、トークンが十分に長い乱数だから
（bcrypt 等が要るのは総当たりが現実的な低エントロピーの秘密＝パスワードを守るとき）。

### AllowedGithubId

| フィールド | 型 | 備考 |
|---|---|---|
| github_id | integer | 主キー |
| note | string | 任意。誰なのかのメモ |
| created_at | datetime | |

### Timeline

| フィールド | 型 | 備考 |
|---|---|---|
| id | ID | |
| owner_id | ID (User) | 所有者。1 ユーザーが複数保持できる |
| slug | string | URL 用。同一オーナー内で一意 |
| title | string | 例: 「SF・コンピューター技術ライフライン」 |
| description | text | 任意 |
| created_at / updated_at | datetime | 一覧は updated_at 降順で並べる |

**`updated_at` は、配下のイベントの追加・編集・削除でも更新する。**
一覧が更新順なので、ここを触らないと並びが機能しない。

### Event

| フィールド | 型 | 備考 |
|---|---|---|
| id | ID | |
| timeline_id | ID (Timeline) | **暫定的に一対多**。将来の多対多化を見越し、中間テーブルへ移行しやすい形にしておく |
| year | integer | 必須 |
| month / day | integer | 任意 |
| hour / minute | integer | 任意。スキーマ上は用意するが MVP の UI では扱わない |
| precision | enum | **時間の粒度**。`century` / `decade` / `year` / `month` / `day` / `minute`。MVP では実質 `year` 固定だが、フィールドは最初から持たせる |
| title | string | 必須 |
| description | text | 任意。元データの「蘊蓄」がここに入る |
| category | string | 任意・**暫定**。元データの `cat`（`sf` / `tech` / `music`） |
| subcategory | string | 任意・**暫定**。元データの `s`（`pc` / `ai` / `game` 等 19 種） |
| links | JSON (text) | 任意。出典・参考リンクの配列。**複数持てる** |
| created_by | ID (User) | 追加した人 |
| created_at / updated_at | datetime | |

**カテゴリを 2 カラムに分ける理由**: MVP の問い「カテゴリは独立したタイムラインに
分けるべきか、タグ的な属性に留めるべきか」を検証するには、両方の粒度が必要になる。
`"tech/pc"` のような複合文字列にすると、あとで分解する手間が来るだけ。
後でタグテーブルに移すのも `INSERT ... SELECT` 一発で済む。

**リンクを JSON 1 カラムにする理由**: MVP では表示するだけで、検索も結合もしない。
専用テーブルに割るのは早すぎる。元データの記法をそのまま保持できるので往復も効く。
D1 は SQLite なので、必要になれば JSON 関数も使える。

**リンクの記法**（元データ由来。パーサを 1 つ書いて表示時に展開する）

| 書き方 | 意味 |
|---|---|
| `"階差機関"` | 日本語版 Wikipedia の記事名 |
| `"en:Analytical Engine"` | 英語版 Wikipedia の記事名 |
| `"記事名\|表示名"` | 表示名を変える |
| `"https://example.com/\|表示名"` | 外部リンク |

**時間の扱いの方針**

最終的には「1990 年代」「18 世紀」のような粗い指定から、
「何年何月何日何時何分」のような細かい指定まで許容したい。
ただし MVP では入力・表示ともに年単位に限定し、
`precision` フィールドによって**後から拡張できる柔軟性だけ確保しておく**。

元データには月日が一件も含まれていないため、この判断は実データに裏打ちされている。

**並び順**: year → month → day → hour → minute → id の昇順。
下位の値が空のものはその区切りの先頭に置く。

### 削除

**物理削除**とする。MVP はデータを入れ直せる段階であり、
全クエリに `deleted_at IS NULL` が混ざるコストのほうが今は高い。

## 8. 初期データ投入について

### 8.1 出典

- リポジトリ: https://github.com/matsuo-koya/sf-tech-lifeline
- ライセンス: **MIT**
- 松尾さんとは共同制作として話がついており、**利用の許可は取得済み**

### 8.2 データの実態

`src/events.js` に `export const EVENTS = [...]` として構造化済みで置かれている。
**スクレイピングは不要**で、import して変換するだけでよい。

| 項目 | 実データ |
|---|---|
| 件数 | 720 件 / 1822〜2026 年（114 年分に分布） |
| `cat` | `tech` 557 / `sf` 96 / `music` 67 |
| `s`（分野） | 19 種（pc 138, game 75, ai 65, video 44 …）。SF 作品 96 件は `s` なし |
| `n`（蘊蓄） | 全件あり。中央値 142 字、最長 1013 字 |
| `l`（リンク） | 全件あり。計 1016 本（1 本:450 / 2 本:250 / 3 本以上:20） |
| 月日 | **一切なし。全て年単位** |
| 最も密な年 | 1982 年の 22 件 |

元データ 1 行のフィールドと投入先の対応:

| 元 | 投入先 |
|---|---|
| `y` | `year`（`precision` は全件 `year`） |
| `t` | `title` |
| `n` | `description` |
| `cat` | `category` |
| `s` | `subcategory` |
| `l` | `links`（JSON 配列としてそのまま） |
| `ic` / `q` / `a` | **捨てる**（アイコン名 / 検索クエリ / 追加日） |

### 8.3 「テーマの糸」について

`src/threads.js` に 20 本の「テーマの糸」がある。
「機械が歌えるようになるまで」（11 項目、1957→2025）のように、
**年表を横断して関連項目を年代順に拾い直す**仕組み。

```js
{ key: "voice", title: "機械が歌えるようになるまで",
  lead: "計算機に音を出させた日から、歌詞を打てば歌になる時代まで、67年かかった。",
  items: [{ y: 1957, m: "MUSIC I" }, { y: 1961, m: "デイジー・ベル" }, …] }
```

これは 6.2 で先送りした**イベントの多対多所属**と
**タイムラインをクエリとして動的に評価する仕組み**そのものである。
元データの作者が既に必要としてそこに到達している。

MVP で先送りする判断は変えない。ただし「いつか来るかも」ではなく**確実に来る**と
わかった以上、`Event.timeline_id` の一対多は本当に暫定として扱うこと。

### 8.4 投入先とオーナーシップ

`/@matsuo-koya/sf-tech-lifeline` に投入する。

`matsuo-koya` の User レコードを**先行して作成**し、そこをオーナーとする。
本人がログインした瞬間、`github_id` の一致で何もせずとも自分のものになる。

```
github_id: 235002527  username: matsuo-koya  display_name: Koya Matsuo
avatar_url: https://avatars.githubusercontent.com/u/235002527?v=4
```

これは「github_id が不変キー」という設計の実地検証を兼ねる。
未登録ユーザーのレコードを先に作れるかどうかは、この先フォークや
共有客観 DB をやるなら必ず踏む道なので、今のうちに一度通しておく。

**`category` ごとに 3 本へ割って投入する。** slug は category のキーと揃える。

| slug | title | 件数 | 年の範囲 |
|---|---|---|---|
| `sf` | SF作品 ライフライン | 96 | 1937〜2021 |
| `tech` | 実テクノロジー ライフライン | 557 | 1822〜2026 |
| `music` | 音楽・カルチャー ライフライン | 67 | 1824〜2025 |

`description` はいずれも **TODO: 書き下ろす**。元 README の「生年を入力すると…」は
アプリの説明であって年表そのものの説明ではないため流用できない。

**当初は 720 件を 1 本の混在版（`sf-tech-lifeline`）として投入していた。**
問い 2（カテゴリは独立したタイムラインに分けるべきか）を実地で見るために割り、
混在版は削除した。変換スクリプトも 3 本を吐くように書き換えてあるので、
混在版はもう再生成されない。復元したい場合は変換スクリプトの旧版を git 履歴から取る。
元データ自体は固定コミットから何度でも取り直せる。

### 8.5 投入手順

1. `events.js` を import し、8.2 の対応で変換
2. `category` ごとに 3 本へ振り分ける（知らない `category` が来たら落とさず失敗する）
3. 変換結果を目視で確認
4. インポートスクリプトで D1 に投入

```bash
pnpm data:convert        # 取得 → 変換 → data/ に JSON と SQL
pnpm data:import         # 本番 D1 に投入（流し直すと入れ替わる）
```

## 9. 確認したいこと（この MVP で答えを出したい問い）

1. 1 本のタイムラインに全カテゴリを混在させたとき、読み物として成立するか
2. カテゴリは独立したタイムラインに分けるべきか、タグ的な属性に留めるべきか
   （`category` / `subcategory` の 2 階層のうち、どちらが分割の単位として自然か）
3. 年単位の粒度で足りるか。年代・期間・月日以下がどれくらい必要になるか
4. 元データ 1 行 = 1 イベントの粒度が、実際に見たときに適切か
5. 複数人がそれぞれのタイムラインを作ったとき、どこで違和感が生まれるか
   （松尾さんという実際の共同制作者相手に初日から検証できる）
